# Design

## Context

See `proposal.md` for motivation and `specs/task-board-keyboard-navigation/spec.md` for the behavior contract. `TaskBoard.vue` already derives both a flattened visible task order and per-status-column task IDs. Vertical movement currently uses `nextVisibleTaskId`, which wraps through the flattened order; horizontal movement uses the per-column lists and skips empty columns. Keyboard shortcut eligibility is centralized in `taskBoardShortcuts.ts`, while card-focused navigation is routed through `TaskCard.vue`.

The task board already protects editable controls, terminal input, open dialogs, and composing key events from shortcut handling. Preserve these guards and keep navigation logic framework-free and unit-testable in `src/domain/`.

## Goals / Non-Goals

**Goals:**

- Make vertical movement bounded to the focused task’s visible status column.
- Add `gg` and uppercase `G` motions over the current visible board order.
- Preserve horizontal movement, initial navigation from the search field, filtering, and shortcut eligibility safeguards.
- Keep the user-facing keyboard help and approved task-workspace behavior documentation aligned.

**Non-Goals:**

- Change task ordering, status grouping, filtering, or horizontal movement behavior.
- Add a general-purpose Vim command parser or change keyboard behavior outside the Tasks view.
- Change the board layout, visual tokens, or backend/task data model.

## Decisions

### Use the existing per-column visible task lists for vertical movement

Resolve the focused task’s column and row from the lists already derived from filtered task groups. ArrowDown/`j` and ArrowUp/`k` select only the next or previous item in that column and return no target at its edges. Keep the flattened list for whole-board ordering and first/last jumps. This avoids changing horizontal navigation or treating adjacent columns as vertical neighbors; replacing the three panes with one visual row-major order was considered and rejected because it preserves the reported surprise.

### Resolve `gg` and `G` against the filtered whole-board order

Use the flattened visible task IDs, which already follow Pending, In progress, and Other statuses order after search and project filtering. `gg` targets the first ID and uppercase `G` targets the last; when the list is empty, leave focus unchanged. This makes “first and last” consistent regardless of the pane where focus currently sits.

Recognize `gg` as two consecutive eligible `g` key events within a 500 ms window. A lone `g` does not move focus, and an unrelated key, an ineligible target, a dialog, or a composing event clears the pending sequence. Accept `G` as the uppercase Vim motion generated by Shift+G, while still rejecting Command, Control, and Alt modifiers and repeated key events. A short explicit window prevents a stale `g` from combining with a later unrelated action; the 500 ms value is an implementation choice, not a user-configurable setting.

### Keep shortcut resolution pure and guards consistent

Put target resolution and key-sequence decisions in domain helpers with explicit inputs so Vitest can cover boundary, filtering, modifier, and sequence cases without mounting Vue or a browser. Keep DOM focus transfer in `TaskBoard.vue`. Route both board-level shortcuts and card-level key events through the same navigation outcome, while retaining the current editable-control, terminal-input, dialog, and composition guards. Do not take `g`/`G` input from search or other editors.

Update the task card’s `aria-keyshortcuts` and the search field’s visually hidden help to advertise the added motions. Update only the keyboard-navigation subsection of `docs/design/SPEC.md`; keep all approved visual design choices unchanged.

## Risks / Trade-offs

- [A task at a column edge no longer advances to the next column with vertical keys] → Keep ArrowLeft/ArrowRight and `h`/`l` as the explicit horizontal controls, and document the distinction in keyboard help.
- [A delayed second `g` could be mistaken for a new `gg` sequence] → Expire the pending first `g` after 500 ms and clear it on unrelated or ineligible key events.
- [Search/project filtering can change the jump targets] → Resolve both targets from the current visible task IDs rather than the unfiltered store contents, and test filtered and empty lists.

## Migration Plan

No data migration or rollout flag is needed. Update the navigation helpers, shortcut handling, focused-card shortcut semantics, unit tests, and the task-workspace keyboard documentation together. Roll back by reverting those source, test, and documentation changes; no persisted user state is affected.
